# VS Code 预览性能与滚动诊断

2026-10-07，macOS arm64。本次将「打开到首屏」「修改到完成帧」「滚动画面」分别测量；字体体积下降不能等同于延迟同比下降。

## 已修复的问题

- **旧工具栏残留**：安装 VSIX 后，复用已有窗口可能继续运行旧的扩展进程，出现旧 HTML 与新 CSS 不匹配。更新后需要重载窗口；预览现通过序列化恢复原标签。
- **触底后向上滚的跳变**：旧适配器在 `edge=end` 时把源码定位强制改为 EOF，其余位置按预览顶部正文映射。一离开底部，两种坐标规则就发生切换。现移除此特殊分支，始终使用连续的正文坐标映射。代价是预览触底时，源码不一定也精确触底；两边优先对齐正在阅读的内容。
- **初始化串行等待**：WASM 初始化与字体文件读取改为并行；仍使用 MVaaC 的共享初始化 Promise，不创建第二个引擎。

## 打开到首屏

真实安装的 VSIX、短文档、已建立字体索引的一次样本：

| 阶段 | 时间 |
| --- | ---: |
| 调用打开命令到 Webview ready | 127 ms |
| 字体查找 | 61 ms |
| 调用打开命令到完成帧反馈 | 455 ms |

这些计时不包括 VS Code 应用冷启动和扩展激活之前的时间，也不等同于显示器上的像素呈现时间。集成测试关闭了后台渲染节流，因此不能排除真实窗口被遮挡时的调度问题。

系统字体索引单独测量：423 个文件，首次建立约 463 ms，缓存后约 11 ms；其他热扫描样本为 19–23 ms。首次安装与随后打开必须分开评价。

以下使用相同的 5,553 字试用文档、本机 HTTP、全新 Chromium context、热操作系统文件缓存。每组 3 次取中位数。绘制使用 headless Chromium 的软件后端，不代表实际 VS Code 的硬件 GPU；表内串行阶段用于归因，生产适配器现已并行初始化 WASM。

| 字体策略 | 字体输入 | 文件读取 | WASM | 字体集解析/复制 | 挂载到完成帧及后续两帧 | 合计 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 旧版全部加载 | 273.1 MiB | 96.7 ms | 20.4 ms | 23.3 ms | 221.5 ms | 362.6 ms |
| 无 Emoji 时跳过 Emoji | 89.9 MiB | 38.7 ms | 21.0 ms | 8.4 ms | 212.5 ms | 280.4 ms |
| 只加载正文/代码字体的实验 | 65.3 MiB | 31.2 ms | 20.3 ms | 5.8 ms | 205.5 ms | 262.8 ms |

最后一项**没有启用**：直接减少字体角色可能改变标题、中文代码等样式。相比已实施方案，它仅再改善约 18 ms，不值得先牺牲字体正确性。

内置 Markdown 组件的本地代码走 Markdown → HTML → 浏览器 DOM/CSS/系统字体。通过安装版本的 `markdown.api.render` 对同一试用文档测量：首次转换约 38 ms，随后约 0.5–0.7 ms。其生成的 HTML 配合原生 `markdown.css`，在独立 Chromium 页面中插入及布局约 30.5–39.6 ms，等待后续两帧约 33.5–55.8 ms。它们是组件阶段数据，**不是内置预览完整首屏时间**，不能与上面的 455 ms 直接计算倍数。

主要差别是 MVaaC 需要取得字体二进制、复制到 WASM、建立自己的 renderer 和字体图集；DOM 预览复用浏览器的字体与排版管线。复用 MVaaC 代码并不会自动消除这些运行时成本。

## 修改到画面更新

复用同一个 Viewer 和字体集，在文档中间插入修改；记录 `setMarkdown` 到 `onStats.pending=false` 的完成帧。不是仅计算 Markdown 解析时间。

| 样本 | 完成帧 | 排版 CPU 时间 | 未变化块复用 |
| --- | ---: | ---: | ---: |
| 5,553 字、多段落 | 15–18 ms | 0.3–0.5 ms | 68 |
| 55,530 字、多段落 | 12.5–22 ms | 热更新 0.3 ms | 热更新 689 |
| 33,000 字、一个超长段落 | 33–42 ms | 28–33 ms | 0 |

每隔 16 ms 发起一次、共 20 次更新后，最后一次到完成帧分别约 18、17、34 ms。此实验的输入发生在浏览器线程；线程阻塞会推迟后续定时器，不能据此声称任意输入速率都没有积压。

真实 VSIX 的短文档修改样本，编辑事件到完成帧消息为 **7–11 ms**。另在真实 VS Code 中加载 5,553 字试用文档，保持源码编辑器激活，三次修改分别为 **8、4、3 ms**；间隔 16 ms 的 20 次连续编辑，最后一次到完成帧为 **9 ms**。普通修改没有复现用户描述的明显等待，因此不能将更新迟缓归因于每次字体扫描或完整重排：字体列表已缓存，未变化块也确实复用。仍需捕获用户实际文档、窗口可见状态与输入操作下的慢样本。

超长单段则存在明确瓶颈：8 ms 的布局步进预算不能打断一次耗时 28–33 ms 的段落处理。提高预算会加剧主线程阻塞；延长防抖会直接增加输入到画面的延迟，都不是理想的首选。

已加入 `Markview` 输出通道的启动阶段记录；编辑到完成帧超过 100 ms 时会输出 `[preview slow update]`，附带解析、排版、绘帧、块复用及 GPU 后端信息。诊断 API 同时保留 `firstRenderMs` 和 `lastEditToRenderMs`。

## 滚动画面与同步策略

引擎级 120 帧滚动样本：帧间隔中位数 16.6 ms、P95 18.4 ms，CPU 绘帧中位数约 1.1 ms。它不含 VS Code 宿主的 `revealRange()` 和实体触控板输入，不能据此宣称真实试用窗口绝不卡顿。

更稳妥的同步方式是：当前操作的一侧拥有控制权 → 读取视口顶部正文锚点 → 插值到另一侧 → 合并宿主定位消息 → 忽略由跟随产生的反馈。两边独立排版，不用全文百分比代替正文位置。底部也应继续使用同一映射，避免突然切换到 EOF。

内置 Markdown 组件也采用源码行及行内比例、约 50 ms 合并和 `revealRange(AtTop)`；公开 VS Code API 没有提供源码编辑器的任意像素 `scrollTop` 控制。因此当前方案可以消除端点断层，但不能保证源码侧具有与 Canvas 完全相同的逐像素滚动。若以后必须同时精确对齐两端，需要新增连续的视口端点校准，而不是恢复触底跳转。

## 后续优化顺序

1. **捕获真实慢更新**：先看慢日志是高排版时间、高绘帧时间，还是低 CPU 时间但高端到端延迟；最后一种优先检查 Webview 可见性、消息调度和资源等待。不要先把普通输入统一延迟 200–300 ms。
2. **减少打开时重复初始化**：尽量复用已打开预览的 Viewer/字体集；需要区分保留 Webview 的内存成本与关闭后的释放。现已有隐藏时保留上下文，真正关掉面板则会释放。系统字体元数据缓存继续保留。
3. **静止时停止不必要的绘制**：当前 reader 每次 RAF 都调用 `frame()`，Rust 端也会提交一帧。改成变化驱动，但需要覆盖滚动惯性、拖选、悬停、图片完成、缩放和布局发布等唤醒条件；不能简单停止 RAF。
4. **拆分超长段落工作**：让 shaping/断行任务可分片，或将解析、布局移到 Worker。Worker 要设计版本取消、字体所有权和几何结果传输；把 Viewer 简单包在 Worker 里不可行。
5. **进一步减小字体传输**：按字体角色、字重和 TTC face 缓存所需字体；子集化必须保留 shaping、变体和授权信息，不能随意裁表。必要时加入无跳版的渐进加载策略。

本轮只落地低风险的同步断点修复、初始化并行和诊断记录；Worker、段落分片、变化驱动绘制与字体子集化仍是方案，未实现。
